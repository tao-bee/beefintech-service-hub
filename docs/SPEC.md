# BeeFintech Service Hub 需求文档

## 1. 文档信息

- 项目名称：BeeFintech Service Hub
- 文档类型：SPEC 需求文档
- 当前版本：v0.1
- 适用阶段：Vibe Coding 实战成长赛第一版交付
- 目标交付时间：5 月 15 日前

## 2. 项目背景

BeeFintech 当前官网主要承担品牌展示和业务介绍职责。为了满足比赛要求，并提升官网的实际服务能力，本项目计划将官网升级为一个轻量化保险科技 Web 服务平台。

升级后的平台不只展示公司能力，还需要承接客户咨询、提供自助查询、辅助客户理解产品价值，并通过更新日志和术语词典形成持续服务入口。

项目需要兼顾三类目标：

- 对外展示：清楚传达 BeeFintech 的保险科技服务能力和客户价值。
- 服务转化：通过预约演示表单和 API 承接潜在客户需求。
- 增值服务：通过 FAQ、ROI 计算器、更新日志、术语词典等功能，让网站从宣传页变成服务中心。

## 3. 项目目标

### 3.1 业务目标

- 建立一个可演示、可部署、可持续维护的 BeeFintech 保险科技服务中心。
- 提升官网对客户咨询、产品理解和服务转化的支持能力。
- 通过多个轻量增值功能体现保险科技服务平台属性。
- 为团队沉淀 AI 协作开发过程、Prompt、问题解决记录和复盘材料。

### 3.2 产品目标

- 用户进入首页后，能快速理解 BeeFintech 做什么、服务谁、解决什么问题。
- 潜在客户可以通过预约演示表单提交咨询需求。
- 客户或内部同事可以通过 FAQ 查询常见问题。
- 客户可以通过 ROI 计算器初步估算自动化和数字化带来的收益。
- 用户可以查看产品更新日志，了解平台持续迭代情况。
- 用户可以通过术语词典理解保险科技和系统集成中的常见概念。

### 3.3 技术目标

- 使用 Next.js + React + TypeScript + Tailwind CSS 快速搭建平台。
- 使用 Next.js Route Handlers 实现预约演示 API。
- 第一阶段优先使用本地静态数据或 JSON 数据，降低后端复杂度。
- 保持代码结构清晰，便于多人协作和后续扩展。

## 5. 核心场景

### 5.1 场景一：潜在客户了解 BeeFintech 服务能力

用户进入首页，浏览公司介绍、核心能力、服务场景和客户价值，判断 BeeFintech 是否适合自己的保险科技需求。

成功标准：

- 首页首屏能清楚表达平台定位。
- 用户能看到核心能力和典型服务场景。
- 页面提供明确的预约演示入口。

### 5.2 场景二：潜在客户提交预约演示

用户对服务感兴趣，填写预约演示表单，提交姓名、公司、职位、联系方式、需求类型和补充说明。

成功标准：

- 表单字段清晰，必填项有校验。
- 提交后调用 `/api/demo-request`。
- 提交成功或失败后，用户能收到明确反馈。

### 5.3 场景三：客户自助查询常见问题

用户进入 FAQ 页面，按分类或关键词查询产品接入、保司合作、数据安全、实施交付、售后支持等问题。

成功标准：

- 支持关键词搜索。
- 支持分类筛选。
- 问题答案可展开和收起。
- 无搜索结果时有清晰提示。

### 5.4 场景四：客户估算保险科技 ROI

用户进入 ROI 计算器，输入月保单量、人力成本、当前处理时长、预计自动化比例等信息，查看预计节省成本、效率提升和回本周期。

成功标准：

- 输入项含义明确。
- 计算结果实时或提交后展示。
- 页面说明结果为估算值，不作为正式报价。

### 5.5 场景五：用户查看产品更新日志

用户进入更新日志页面，查看不同版本的发布日期、更新类型和功能说明，了解平台持续迭代能力。

成功标准：

- 更新日志按时间倒序展示。
- 每条记录包含版本号、日期、类型和内容。
- 更新类型可清楚区分，例如新增、优化、修复。

### 5.6 场景六：用户查询行业术语

用户进入行业术语词典页面，搜索或浏览保险科技和系统集成相关术语，理解业务沟通中的关键概念。

成功标准：

- 支持关键词搜索。
- 支持按分类浏览。
- 每个术语包含名称、分类、解释和相关场景。

验收标准：

### 8.2 预约演示表单

需求编号：FR-002  
优先级：P0

预约演示表单用于收集潜在客户的咨询和演示需求。

字段要求：

| 字段 | 类型 | 是否必填 | 校验规则 |
| --- | --- | --- | --- |
| 姓名 | 文本 | 是 | 不能为空 |
| 公司 | 文本 | 是 | 不能为空 |
| 职位 | 文本 | 否 | 可为空 |
| 联系方式 | 文本 | 是 | 支持手机号或邮箱格式 |
| 需求类型 | 单选 / 下拉 | 是 | 必须选择一个预设值 |
| 补充说明 | 多行文本 | 否 | 限制最大长度 |

需求类型建议：

- 产品演示
- 系统接入咨询
- 渠道合作
- 数据安全 / 合规咨询
- 售后支持
- 其他

交互要求：

- 必填项为空时给出明确提示。
- 联系方式格式明显错误时给出提示。
- 提交过程中显示 loading 状态。
- 提交成功后显示成功提示。
- 提交失败后显示失败提示，并允许用户重试。

验收标准：

- 表单能完成输入、校验、提交和反馈流程。
- 表单提交会调用预约演示 API。
- 无需刷新页面即可看到提交结果。

### 8.3 预约演示 API

需求编号：FR-003  
优先级：P0

系统需要提供预约演示接口，用于接收前端表单提交的数据。

接口定义：

```text
POST /api/demo-request
```

请求体示例：

```json
{
  "name": "张三",
  "company": "某某保险经纪有限公司",
  "title": "业务负责人",
  "contact": "zhangsan@example.com",
  "requestType": "产品演示",
  "message": "希望了解渠道管理和保单服务能力。"
}
```

成功响应示例：

```json
{
  "ok": true,
  "message": "预约信息已提交，我们会尽快联系您。",
  "requestId": "demo_20260515_001"
}
```

失败响应示例：

```json
{
  "ok": false,
  "message": "请填写姓名、公司、联系方式和需求类型。"
}
```

接口要求：

- 校验必填字段。
- 返回结构化 JSON。
- 第一阶段可以不接数据库，使用 mock 成功响应。
- 如采用本地 JSON 记录，需要避免提交敏感真实客户信息。

验收标准：

- 使用前端表单提交时可以收到成功或失败响应。
- 缺少必填字段时接口返回错误信息。
- 接口响应结构稳定，便于前端处理。

### 8.5 ROI 计算器

需求编号：FR-005  
优先级：P1

ROI 计算器用于帮助客户粗略估算引入保险科技自动化能力后的效率和成本收益。

输入字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| monthlyPolicies | 数字 | 月保单量 |
| laborCostPerHour | 数字 | 人力成本，单位：元 / 小时 |
| minutesPerPolicy | 数字 | 当前每单处理时长，单位：分钟 |
| automationRate | 数字 | 预计自动化比例，范围 0-100% |
| implementationCost | 数字 | 预计实施成本，单位：元 |

输出结果：

- 当前月人工处理成本
- 自动化后预计月节省成本
- 预计效率提升比例
- 预计回本周期

计算说明：

- 当前月人工成本 = 月保单量 × 每单处理分钟数 / 60 × 每小时人力成本
- 预计月节省成本 = 当前月人工成本 × 自动化比例
- 回本周期 = 实施成本 / 预计月节省成本

交互要求：

- 输入非法数字时给出提示。
- 自动化比例应限制在 0 到 100 之间。
- 当月节省成本为 0 时，不展示无意义的回本周期。
- 明确提示计算结果为估算值，不构成正式报价。

验收标准：

- 修改输入后，结果能正确刷新。
- 计算结果格式清晰，金额和周期易读。
- 极端输入不会导致页面异常。

## 10. 非功能需求

### 10.1 可用性

- 页面导航清晰，用户能快速找到预约演示、FAQ、ROI 计算器、更新日志、术语词典。
- 表单、搜索、筛选、展开收起等交互需要有明确反馈。
- 空状态、错误状态和 loading 状态需要可见。

### 10.2 响应式

- 支持桌面端和移动端浏览。
- 移动端导航和表单布局需要可用。
- 文本不应溢出按钮、卡片或输入框。

### 10.3 性能

- 第一屏加载应尽量轻量。
- 静态内容优先本地渲染。
- 避免不必要的大型依赖。

### 10.4 可维护性

- 使用 TypeScript 类型约束主要数据结构。
- 页面组件和数据文件分离。
- 公共 UI 组件放在 `src/components/`。
- 业务计算逻辑放在 `src/lib/`，例如 ROI 计算函数。

### 10.5 安全与隐私

- 预约演示表单不要在前端暴露敏感配置。
- 不提交真实客户隐私数据到公开仓库。
- API 对输入数据做基础校验。
- 如后续接入数据库或第三方系统，需要补充数据安全说明。

- FAQ 页面可访问，支持搜索、分类和展开收起。
- ROI 计算器可访问，输入参数后能输出估算结果。
- 更新日志页面可访问，至少展示 3 条更新记录。
- 术语词典页面可访问，至少展示 10 个术语，并支持搜索和分类。

### 12.3 文档验收

- `README.md` 已作为项目说明入口。
- `docs/SPEC.md` 已包含需求说明。
- 后续需要补齐 `docs/PLAN.md`、`docs/AI_COLLABORATION.md`、`docs/TESTING.md`、`docs/RETROSPECTIVE.md`。

### 12.4 工程验收

- 项目能本地启动。
- 项目能通过构建命令。
- 主要页面无明显控制台错误。
- 桌面端和移动端布局可用。
- 关键交互有基础测试或手动测试记录。

## 13. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 时间有限，功能过多 | 可能导致功能半成品 | 严格先做 P0 和 P1，不提前投入后台和登录 |
| 真实 API 或数据源缺失 | 影响预约演示闭环 | 第一版使用 mock API，保留后续对接扩展点 |
| 内容质量不足 | 页面显得空泛 | FAQ、术语、更新日志使用贴近保险科技场景的示例 |
| 多人协作冲突 | 影响提交和合并 | 按页面或文档拆分分支，每人负责独立范围 |
| 只重结果不留过程 | 影响比赛过程分 | 每阶段记录 Prompt、改动、验证、问题和复盘 |
