# BeeFintech Service Hub 当前阶段执行规划

## 1. 文档目的

本文档用于指导 BeeFintech Service Hub 在 Vibe Coding 实战成长赛当前阶段的执行工作，重点服务于阶段性交付、过程证据整理和团队协作推进。

本文档不是长期产品路线图，也不是后续全部功能的一次性开发计划，而是围绕当前阶段三条功能分支的成果整理、验证、合并准备和材料沉淀展开，确保项目既能展示业务价值，也能满足比赛对过程质量的要求。

适用对象包括：

- 开发同学：确认当前阶段代码范围、页面能力和验证动作
- 内容同学：整理 FAQ 文案、页面说明和比赛展示口径
- 测试同学：记录验证结果、页面体验和问题清单
- 比赛材料整理同学：补齐执行规划、AI 协作记录、测试说明和复盘材料

本文档需要与以下文件配套使用：

- `README.md`：项目目标、时间节点、交付要求和功能优先级
- `docs/SPEC.md`：需求范围、页面结构和验收标准
- `docs/FAQ.md`：FAQ 功能方案、数据结构和交互说明
- `docs/AI_COLLABORATION.md`：AI 协作过程、Prompt 类型、人工调整和补救记录
- `docs/TESTING.md`：命令验证、页面验收清单和待人工复核项
- `docs/RETROSPECTIVE.md`：阶段复盘、问题总结和后续改进建议

## 2. 当前阶段目标

当前阶段的目标不是继续扩展全部 P1 功能，而是围绕三条已开出的功能分支完成阶段性交付确认、统一合并准备和比赛材料补齐。

本阶段重点聚焦以下三组功能能力：

- 品牌宣传首页
- 预约演示表单与 `POST /api/demo-request`
- FAQ 自助查询页面 `/faq`
- 行业术语词典页面 `/glossary`

本阶段目标包括：

- 确认首页及预约演示、FAQ、行业术语词典三个功能方向都已形成可演示的阶段成果
- 保持需求文档、功能方案和实际实现一致，避免文档与代码脱节
- 为三个分支后续统一合并到主开发线做准备
- 补齐当前阶段执行规划、测试说明、AI 协作记录和复盘准备材料
- 为下一阶段扩展 ROI 计算器、产品更新日志等功能保留结构基础

说明：

- 本阶段不将 ROI 计算器、产品更新日志纳入主合并范围
- 本阶段优先完成“三个功能分支收口 + 合并准备 + 过程证据补齐”

## 5. 角色分工

当前阶段采用按角色分工的方式，不在文档中写具体成员姓名，便于后续由团队自行对应实际负责人。

### 5.1 前端实现角色

职责范围：

- 检查首页、FAQ、行业术语词典页面布局、交互和响应式表现
- 确认页面入口、导航、按钮状态和文案展示是否可用
- 保证新增页面不破坏现有首页预约演示闭环

### 5.2 接口验证角色

职责范围：

- 验证预约演示表单字段与接口约定一致
- 检查必填校验、联系方式格式校验和返回结构
- 确认成功、失败和异常场景的接口反馈完整

### 5.3 内容与文档角色

职责范围：

- 维护 FAQ、行业术语词典文案、页面说明和业务措辞
- 补齐 `docs/PLAN.md`、`docs/TESTING.md`、`docs/AI_COLLABORATION.md`、`docs/RETROSPECTIVE.md`
- 保证 README、SPEC、功能方案与代码行为一致

### 5.4 合并协调角色

职责范围：

- 统筹三个功能分支的合并顺序和冲突处理
- 确认路由、导航、服务工具入口和文档表述一致
- 在合并前后检查首页及预约演示闭环是否稳定

### 5.5 测试与验收角色

职责范围：

- 执行命令验证和手动页面验证
- 记录问题、现象、复现路径和处理状态
- 输出阶段验收结论，支持比赛展示和团队交接

## 7. 风险与应对

### 7.1 文档与实现不一致

风险：

- 页面行为已调整，但 `SPEC`、`FAQ` 方案或执行规划未同步更新

应对：

- 每次涉及路由、字段、交互或验收标准变化时，同步更新对应文档
- 以当前仓库实际实现为准，不虚构已完成能力

### 7.2 只完成功能但缺少过程证据

风险：

- 比赛只能看到结果，无法体现 AI 协作、验证过程和问题解决能力

应对：

- 补齐 `docs/PLAN.md`、`docs/AI_COLLABORATION.md`、`docs/TESTING.md`、`docs/RETROSPECTIVE.md`
- 记录关键 Prompt、实现过程、验证命令和人工调整内容
- 后续新功能在实现前先补充 superpowers 计划，减少事后补录

### 7.3 P1 范围膨胀导致当前阶段失焦

风险：

- 在当前阶段继续扩展 ROI、更新日志等新功能，导致三个既有分支收尾不足

应对：

- 当前阶段只把首页及预约演示、FAQ、行业术语词典和比赛材料补齐作为主线
- 其他 P1 功能留到下一阶段单独规划和实现

### 7.4 多人协作时提交范围混乱

风险：

- 三个分支同时修改导航、服务工具入口、文档和数据结构，影响 review、提交和合并质量

应对：

- 保持首页及预约演示、FAQ、行业术语词典三个功能分支职责边界清晰
- 提交前检查 `git status` 和 `git diff --stat`
- 合并前统一核对文档、路由和入口配置
