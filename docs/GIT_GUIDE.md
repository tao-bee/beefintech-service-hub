# Git 简明协作指南

本文面向不熟悉技术的团队成员。你不需要记住所有 Git 命令，可以把本文当成和 AI 协作时的操作手册：先看懂每一步的目的，再让 AI 帮你执行。

## Git 是什么

Git 可以理解为项目的“版本记录本”。

- 每次改动都可以被记录下来，形成一次 `commit`。
- 每个人的修改都能留下名字和时间，方便比赛展示多人协作过程。
- 如果改错了，可以通过历史记录找到之前的版本。
- 大家可以在不同分支上工作，再把成果合并到主分支。

## 常见词汇

- 仓库 `repository`：整个项目文件夹。
- 分支 `branch`：一条独立工作线。本项目常用 `main`、`dev` 和 `feature/xxx`。
- 主分支 `main`：稳定版本，通常用于最终展示或部署。
- 集成分支 `dev`：用来汇总各功能分支的阶段性成果，正常开发不直接在这里改。
- 提交 `commit`：一次有说明的改动记录。
- 推送 `push`：把本机提交上传到远端仓库。
- 拉取 `pull`：把远端最新内容同步到本机。
- 合并 `merge`：把一个分支的改动合到另一个分支。
- 冲突 `conflict`：两个人改了同一个地方，Git 不知道该保留哪一版，需要人工确认。

## 本项目分支约定

- `main`：稳定分支，阶段性完成后再合并进去。
- `dev`：集成分支，正常开发不直接在 `dev` 上修改。
- `feature/xxx`：个人或单项任务分支，一个功能或一类文档任务对应一个分支，例如 `feature/docs`、`feature/faq`。

团队成员应优先在自己的 `feature/名字-任务` 分支上提交文档、文案、测试记录和截图说明。完成后把分支推送到远端，再经过检查后合并到 `dev`。

说明：项目初始化阶段为了快速搭建基础结构，可能会临时直接在 `dev` 上操作。进入常规协作后，应回到“一个功能一个分支”的流程。

## 日常协作流程

### 1. 开始工作前同步最新代码

目的：避免在旧版本上修改。

可以对 AI 说：

```text
请检查当前 Git 状态，切换到 dev 分支，并拉取远端最新代码。完成后不要直接在 dev 上改内容。
```

AI 通常会执行：

```bash
git status
git switch dev
git pull
```

### 2. 为本次任务创建功能分支

目的：一个功能或一类文档改动使用一个独立分支，避免多人互相影响。

可以对 AI 说：

```text
请基于最新 dev 创建一个新分支 feature/docs-我的名字，用来修改项目文档。
```

AI 通常会执行：

```bash
git switch -c feature/docs-your-name
```

分支命名建议：

```text
feature/faq
feature/roi-calculator
feature/docs-name
feature/testing-notes
feature/homepage-copy
```

### 3. 修改文件

可以让 AI 帮你改文档、补页面文案、整理测试记录，或者你自己直接编辑文件。

适合非技术同事提交的内容包括：

- 需求说明
- 页面文案
- FAQ 问答内容
- 测试记录
- AI 协作记录
- 复盘总结
- 演示说明

### 4. 提交前检查改了什么

目的：确认只提交本次任务相关内容。

可以对 AI 说：

```text
请检查当前 Git 改动，告诉我改了哪些文件，不要提交。
```

AI 通常会执行：

```bash
git status
git diff --stat
```

### 5. 提交到本地

目的：把本次改动记录成一次可追踪的历史。

可以对 AI 说：

```text
请把这次关于「补充测试说明」的改动提交到 Git，提交信息用中文或英文都可以，要求清楚说明做了什么。
```

AI 通常会执行：

```bash
git add <相关文件>
git commit -m "docs: add testing notes"
```

提交信息建议格式：

```text
docs: update testing notes
feat: add FAQ content
fix: update favicon config
chore: organize project docs
```

常见类型：

- `docs`：文档修改
- `feat`：新增功能
- `fix`：修复问题
- `chore`：整理、配置、杂项
- `test`：测试相关

### 6. 推送到远端

目的：把自己的提交上传，让其他成员和评委能看到。

可以对 AI 说：

```text
请把当前分支 push 到远端。
```

AI 通常会执行：

```bash
git push
```

如果是第一次推送新分支，AI 可能会执行：

```bash
git push -u origin feature/your-task
```

### 7. 准备合并

目的：让团队知道这个分支已经完成，可以检查后合并到 `dev`。

可以对 AI 说：

```text
请确认当前 feature 分支已经提交并推送，然后总结本分支改了什么，方便团队检查后合并到 dev。
```

## 推荐给非技术同事的 AI 提示词

### 查看当前状态

```text
请检查当前项目的 Git 状态，告诉我现在在哪个分支、有没有未提交的改动、是否落后或领先远端。
```

### 开始一个文档任务

```text
请基于最新 dev 分支创建一个新分支 feature/docs-我的名字，用来修改项目文档。创建前先确认工作区是否干净。创建后停在 feature 分支，不要直接在 dev 上修改。
```

### 提交自己的文档改动

```text
请检查我刚才修改的文档内容，确认没有误改代码文件后，把相关文档提交到 Git。提交信息要说明我完成了什么文档。
```

### 推送自己的分支

```text
请把当前分支推送到远端仓库。如果这是第一次推送该分支，请设置 upstream。
```

### 合并到 dev

```text
请先确认当前 feature 分支已经提交并推送，然后切到 dev，拉取远端最新代码，再把该 feature 分支合并到 dev。如果有冲突，先停下来解释冲突内容，不要直接覆盖。
```

说明：合并前要先确认 feature 分支已经提交并推送，且当前工作区干净。遇到冲突时先解释冲突，不要直接覆盖内容。

### 合并 dev 到 main

```text
请把 dev 分支合并到 main 分支，并 push 到远端。合并前先确认 dev 和 main 的状态。
```

## 多人协作时的安全规则

- 开始工作前先 `pull`，避免基于旧代码修改。
- 常规开发不要直接在 `dev` 或 `main` 上改内容。
- 一个功能、一个页面或一类文档任务，尽量对应一个 `feature/xxx` 分支。
- 提交前先看 `git status` 和 `git diff --stat`。
- 只提交和本次任务有关的文件。
- 不要让 AI 执行 `git reset --hard`，除非你非常确定要丢弃本地改动。
- 不要让 AI 执行 `git checkout -- 文件名` 来丢弃改动，除非确认这些改动不需要了。
- 遇到冲突时，不要慌，先让 AI 解释冲突文件和冲突原因。
- 每位成员至少保留一次自己的 `commit`，这样比赛能看到多人协作记录。

## 出问题时怎么问 AI

如果不确定当前状态，可以直接说：

```text
我不懂 Git，请你先不要修改文件，也不要提交。请只检查当前 Git 状态，并用普通话解释我现在应该做什么。
```

如果 push 失败，可以说：

```text
刚才 git push 失败了。请根据错误信息判断原因，先解释问题，再告诉我是否需要重新登录、联网、pull，或者处理冲突。
```

如果出现冲突，可以说：

```text
Git 提示有冲突。请列出冲突文件，解释每个冲突大概是什么，不要直接覆盖任何人的内容，先给我建议。
```

## 最小记忆版

如果只记住一套流程，记下面这套：

```bash
git switch dev
git pull
git switch -c feature/your-task
git status
git add <本次修改的文件>
git commit -m "docs: describe your change"
git push -u origin feature/your-task
```

不熟悉命令时，不要自己硬敲。直接让 AI 按本文流程检查、解释、执行，会更稳。
